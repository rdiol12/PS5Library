# Storage and inventory

## VERIFIED implementation

Storage planning uses exact paths instead of mutable display IDs. The agent keeps `/data` for private app staging and `/user` for PS5-managed installs, while the storefront presents their shared physical SSD as one **Internal Storage** card. `/mnt/ext1` is the PS5-managed M.2 destination and `/mnt/ext0` is Sony-managed encrypted USB extended storage. Raw `/mnt/usbN` mounts are never FPKG destinations. Homebrew and ShadowMount keep their actual supported storage choices.

The native download sheet selects the first allowed destination when the asynchronous plan arrives, instead of retaining focus on Back. Each destination shows required space or a read-only/unsupported-method reason. `/mnt/ext1` advertises FPKG only when the native AppInst move API is available. `/mnt/ext0` additionally requires its exact managed-UFS mount and a successful guarded external-FPKG patch receipt at `/data/ps5library/external-fpkg-patch.json`. Completion resolves the native location and requires the installed package's physical destination and installed-image hash to match the plan. Insufficient space, a destination mismatch and unsupported installation remain real restrictions.

Configured roots are enumerated with native filesystem space queries and actual write access. The API uses friendly `storageId`/display names; raw paths stay out of normal storefront screens. Unsupported/unwritable destinations are disabled. Planning includes game, update, backport, temporary bytes and safety margin; active transfers reserve capacity. Build output is remeasured before the transfer is queued.

Agent-managed image transfers go to `.ps5library/staging/<job>/content.part` outside watched final folders. The agent checks size and SHA-256 before atomic publication on the same filesystem. Receipts identify the exact release/hash/path and registration state. HTTP Range and strong artifact ETags support continuation after interruption. Remaining-byte checks allow resumed downloads without reserving the completed part twice.

The native base-FPKG route leaves download and installation to the PS5 OS because the verified AppInst URL ABI has no destination argument. Internal installs use the normal target, M.2 selections temporarily select the native M.2 target, and managed-USB selections install internally before using Sony's native move service. The agent then verifies the physical destination and installed-image hash before READY. The Library Node measures unique HTTP Range coverage and derives persisted speed and ETA from bytes actually sent; overlapping retries do not inflate progress. A base FPKG is not routed through a ShadowMount watched folder. End-to-end physical installation, movement, verification and Home launch remain pending.

## EXPERIMENTAL PS5 FPKG on external USB

**VERIFIED BINARY / 4.50 HARDWARE CAPTURE:** the matching console's decrypted 4.50 `SceShellCore` and the earlier 4.51 input are byte-identical (28,371,572 bytes; SHA-256 `8f46f5921b5e75993c6bc3e9141f1d32c898c7beba20ef15cb2f85982a99d4d7`). The process-start check at virtual address `0x531280` takes `je 0x5312dc` only when the install HDD type is external and the application is PS5, producing `0x80A40092` and `[PPRBUG-44860] SCE_APP_INSTALL_HDD_TYPE_EXTERNAL && PS5 app`. This is a launch-policy check; it is not proof that AppInst can select USB.

The production agent applies the same two-byte branch change only after validating the complete ten-byte instruction context. Unknown firmware, module, base or bytes fail before any ShellCore write; the changed bytes are read back before the agent records its exact receipt. The 4.50 hardware capture disproved the earlier inferred address: matching 4.50 and 4.51 inputs both use `0x531280`. The live receipt at `/data/ps5library/external-fpkg-patch.json` reports `APPLIED`.

**ABI AND READ-ONLY HARDWARE VERIFIED / MOVEMENT PENDING:** the live mount probe identifies `/mnt/ext1` (`/dev/ssd1.user`, BFS) as M.2 and `/mnt/usb0` (`/dev/da1p1`, exFAT) as raw USB. `/dev/da1p1` is the mounted exFAT partition; it is not the formatter argument. Raw USB is not native application storage and is never advertised for FPKG. Captured ShellCore verifies the managed-USB contract: `MountExternalHdd` at VA `0x763000` rejects `/dev/da0...`, requires a `.crypt` device, and mounts UFS at `/mnt/ext0` with `alloc_policy=zone`, `nocrypt=yes`, and `removable=yes`. Raw exFAT follows a separate `/mnt/usb%u` mount path.

The AppInst APIs use two different storage enums. `sceAppInstUtilAppGetStorageDestType` requires the full Content ID and reports 1 for internal, 2 for managed USB and 3 for M.2. `sceAppInstUtilAppRequestMoveApps` accepts 0, 1 and 2 for the same destinations. The guarded adapter first calls `sceAppInstUtilAppExists` with the Title ID, validates the query/request offset and global move state, then prepares one zero-padded 12-byte Title ID. A read-only 4.50 probe found `PPSA99783`, returned internal type 1 and left the bounded one-byte result guard intact. It did not submit a move. Host boundaries, the PS5 cross-build and loader checks pass. External FPKG capability is now advertised only through the gates above; physical movement, cancellation and reboot behavior remain unverified.

Turning exFAT into managed type-1 storage is not a path or permission change. ShellCore's official format worker calls `sceFsExternalStorageInitialize` for the whole raw device and writes 0x200-byte main, backup and raw metadata records. The formatter itself does not mount the result. A later automounter pass verifies the metadata, acquires `/dev/es0.crypt`, and mounts that UFS device at `/mnt/ext0`. Firmware 4.50/4.51 refuses acquisition while another encrypted USB device is registered, so the captured implementation supports one managed USB device at a time. Formatting is destructive. PS5Library does not run it automatically and does not alias `/mnt/usb0` to `/mnt/ext0`.

**VERIFIED FORMAT ABI / READ-ONLY 4.50 PROBE:** the live console's `libSceSystemService` was decrypted without modifying it. Export NIDs and disassembly verify `int32_t sceShellCoreUtilFormatExternalHdd(const char*)`, `float sceShellCoreUtilGetProgressOfFormatExternalHdd(void)`, and `int32_t sceShellCoreUtilExfatFormatExternalHdd(const char*)`. The intended native-format argument is the whole raw disk `/dev/daN`, such as `/dev/da1`; it is never `/mnt/usbN` or `/dev/daNp1`. ShellCore requires the `/dev/da` prefix, rejects `/dev/da0...`, and limits the native-format string to less than 64 bytes. The public call blocks until the queued worker returns its final success or error result. Progress is a real current/total ratio sampled concurrently; the worker resets it to `0.0` one second after completion. No formatter cancellation API was found. A linked progress-only probe returned `0.0` and performed no format.

**VERIFIED AUTHORIZATION / HARDWARE FAILURE:** ShellCore checks caller capability word 0 bit 62 before accepting a format job. Payload SDK startup grants this bit, and a live read-only credential probe confirmed it in the running environment. The first explicit request passed this gate and reached `sceFsExternalStorageInitialize`; its `0x80020001` result was therefore not an authorization failure.

**VERIFIED IMPLEMENTATION / FIRST HARDWARE ATTEMPT:** My PS5 shows **Format for PS5** only when the local agent verifies an exact raw `usbN` exFAT device and explicitly reports `formatEligible: true`. The destructive modal shows the exact drive name and byte size, warns that all data will be erased and focuses Cancel by default. Prepare returns a cryptographically random, 60-second, one-use confirmation bound to the mount, partition, whole disk, capacity and exFAT boot identity. Confirm consumes it before repeating the probe; the asynchronous worker probes once more and refuses active staging/ShadowMount use or an existing managed USB.

The first hardware request failed with `0x80020001` before erasure. Decrypted `libSceFsInternalForVsh` shows `sceFsExternalStorageInitialize` tried to create the GEOM CRYPT provider while the exFAT partition remained mounted. A second attempt used normal `unmount(2)` and failed safely with `EBUSY` (`16`): ShadowMountPlus retains watchers for default USB roots, and the agent could rescan while its detached worker was active. A third attempt reached AutoMounter but passed the whole disk `/dev/da1`; ShellCore correctly returned `0x80F40002` because its filesystem-mounted record is `/dev/da1p1`. In every case the formatter remained uncalled and the exFAT volume stayed intact. The corrected agent freezes its own USB scans/media/actions and calls the verified `libSceUsbStorage` AutoMounter export with the exact identity-bound mounted partition. ShellCore routes that `/dev/da*` path through coordinated removable-media cleanup; PS5Library does not issue `MNT_FORCE` itself. It then revalidates both character-device identities and passes only the whole disk to the formatter. The agent samples real progress and waits for verified UFS `.crypt` publication at `/mnt/ext0`; if native formatting succeeds but automount does not, it reports `STORAGE_FORMAT_FINISHED_RECONNECT_USB`. Replay, changed-device, active-operation exclusion, surfaced-native-error, host-build, PS5 cross-build and loader checks pass.

**VERIFIED FORMAT SUCCESS / MOUNT PENDING:** the next physical attempt returned success from `sceShellCoreUtilFormatExternalHdd`. `/dev/da1p1` disappeared and only the raw `/dev/da1` node remained, which is consistent with destructive conversion, but neither `/dev/es0.crypt` nor an exact `/mnt/ext0` mount appeared. A manual guessed `requestMount("/dev/da1")` did not return and produced no mount, so it was killed and removed. Reverse tracing confirms that request requires an already registered exact `UsbDeviceManager` path; it does not resolve disk topology. The exported SystemService and UsbStorage map/unmap calls also require an existing numeric USB device ID and only create or remove a per-process mount. They cannot recreate a partition node or device-manager record.

The lower-level 4.50 `libSceUsbd` exports were then verified on hardware. A read-only descriptor/configuration pass found exactly one device with a mass-storage interface; `sceUsbdResetDevice` opened that exact device and returned `0`. The guarded reset still left only `/dev/da1`, with no `/dev/da1p1`, `/dev/es0.crypt` or `/mnt/ext0`. ShellCore's remaining unregistered-device scan is private and has no verified external IPC entry. PS5Library therefore reports `RECONNECT_REQUIRED` at 100%, sends a native reconnect notice and waits for a physical unplug/replug to drive the normal kernel/devctl enumeration path. Reboot remains a fallback, not the normal instruction.

The reported 1.7 MB USB was the surviving unmounted `/mnt/usb0` directory measured against its tiny backing filesystem, not the formatted drive. The agent now requires `statfs.f_mntonname` to equal every numbered mount and calculates PS5 capacity as checked blocks × block size. The server marks absent volumes inactive only when membership changes, clears their capacity/methods, and omits them from console and transfer responses while retaining rows required by existing job foreign keys. Unchanged heartbeats do not rewrite storage rows.

ShadowMountPlus 1.7 library overlays are staged under `.ps5library/staging/<job>/backport` and hash-verified before a same-filesystem rename into a verified scan root's `backports/<TITLE_ID>`. Conflicting existing overlays block publication; there is no automatic destructive replacement. Selected library paths and hashes are saved in managed receipts and rechecked during inventory reconciliation.

Server cache and console library are separate. Console inventory is authoritative about physical availability. Missing/deleted files cause `MISSING`; the server does not continue showing READY just because it once transferred a file. Complete inventory revisions reconcile expected records. A device cannot report another owner's release.

The scanner reads managed receipts, bounded prepared-dump directories and supported installed PS4 package metadata. Managed files are hashed on first observation and after file size/mtime changes. It does not modify Sony's system databases. The SDK `samples/mntinfo/main.c` verifies that mount enumeration is possible, but arbitrary mounts are not automatically treated as safe install targets.

## UNKNOWN / remaining

Broader native-title inventory, physical managed moves, physical delete validation, removable-drive reconnects and sleep/reboot recovery need hardware work. Destructive initialization and exact `/dev/es0.crypt` → `/mnt/ext0` publication after reconnect have succeeded on hardware; the live move progress curve, power-loss recovery and reboot persistence remain unverified. The captured formatter exposes no cancellation API. Confirmed deletion is implemented and host-tested; it has not deleted any user's console content during development. Configured storage paths and a ShadowMount config file are not sufficient evidence of every filesystem's supported method.

Metadata inspection on the console is not yet as comprehensive as the worker's structural inspection. Hash equality proves the transferred file matches the verified server artifact; it is not an independent launch test. Large-title performance and unusual USB filesystems must be tested before release.
